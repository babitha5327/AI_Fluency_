# Day 6 Assessment – Reliable Tool Calling

## Scenario: Student Study Planner

### 1. Introduction

For this assessment, I built a small Student Study Planner using an OpenAI-compatible API. The purpose of the system is to allow a language model to request simple actions through tools instead of generating all information directly.

The system contains two tools:

1. `get_subject_info` – returns study information for a subject and accepts a controlled priority value.
2. `calculate_study_time` – calculates total study time from the number of subjects and the hours allocated to each subject.

The implementation contains JSON schemas, argument validation, a robust agent loop, deliberate fault injection, and a structured-output demonstration.

The important lesson is that a tool call is generated by the model, so it must be treated as untrusted input. My Python code validates the call before executing the requested function.

---

# 2. Explanation of Concepts

## 2.1 Chat Completions Format

The Chat Completions API sends a request containing the model, messages, and, when tools are available, a `tools` definition. The main request fields used in this project are:

- `model` – the model that should process the request.
- `messages` – the system, user, assistant and tool messages.
- `tools` – the functions that the model is allowed to request.
- `temperature` – controls generation randomness.
- `max_tokens` – limits the generated response.

The response contains `choices`. Each choice contains a message and a `finish_reason`.

The three important `finish_reason` values are:

- `stop` – the model finished normally. If there is no tool call, my code returns the final answer.
- `length` – the response was truncated because the token limit was reached. My agent increases `max_tokens` and retries.
- `tool_calls` – the model requested one or more tools. My code processes every tool call and sends the results back to the model.

When the model wants to use a tool, `message.content` can be empty because the useful information is inside `message.tool_calls`. Therefore, the agent checks `tool_calls` instead of assuming that a normal text answer is always present.

---

## 2.2 OpenAI-Compatible APIs

An OpenAI-compatible server exposes an API with the same general request and response format expected by the OpenAI Python client.

The same client style can therefore be used with providers such as Ollama, vLLM, Groq or Hugging Face when they expose a compatible endpoint. In my project, I selected the provider through environment variables such as `BASE_URL`, `MODEL`, `API_KEY` and `PROVIDER`.

The main change needed to point the client at a provider is the `base_url` and the model configuration.

Compatibility does not mean that every provider supports every OpenAI feature in exactly the same way. For example, support for strict structured-output/schema mode can vary between servers and models.

---

## 2.3 Streaming and the Responses API

Streaming sends generated output in smaller pieces instead of waiting for the complete response. This can improve perceived responsiveness because the user can see output as it arrives.

For an agent loop, streaming is usually switched off because the agent needs the complete response, including all tool calls and their arguments, before it can validate and execute them.

The Responses API uses a different response structure and interaction style from Chat Completions. This course uses Chat Completions because it provides the format needed for the function/tool-calling exercises and keeps the implementation consistent with the earlier labs.

---

## 2.4 Five Steps of a Tool Call

One tool call in my Student Study Planner follows these steps:

1. The user sends a question.
2. The model receives the messages and the available tool schemas.
3. The model generates a tool call containing a tool name and JSON arguments.
4. My Python program parses, validates and executes the requested function.
5. My program sends the tool result back using the corresponding `tool_call_id`, and the model produces the final answer.

The model does not actually execute the Python function. **My code executes the function.**

This distinction is important because the model only generates a request. The arguments must therefore be treated as untrusted input and checked before the function runs.

# 3. Tool Schemas

Each tool has a description and a JSON Schema describing its arguments.

For `get_subject_info`, the schema contains:

- `subject` – a required string.
- `priority` – a string with the enum values `low`, `medium` and `high`.
- `additionalProperties: false` – prevents arguments that are not defined by the schema.

For `calculate_study_time`, the schema contains:

- `subjects` – a required integer.
- `hours_per_subject` – a required number.
- `additionalProperties: false`.

### Purpose of the schema features

| Schema feature | Purpose |
|---|---|
| `description` | Helps the model understand what the tool and arguments mean |
| `properties` | Defines the accepted argument names and types |
| `required` | Prevents required arguments from being omitted |
| `enum` | Restricts a value to an allowed list |
| `additionalProperties: false` | Rejects invented arguments |
| `strict` | Used with structured schema output to require the defined shape |

The schema prevents several predictable mistakes, but it cannot prove that the requested action is logically correct. A correctly shaped argument can still represent an unsuitable request.

---

# 4. Tool Choice

The tool choice options have different purposes:

- `auto` – the model may choose whether to call a tool.
- `none` – the model must not call a tool.
- `required` – the model must call a tool.
- A named function – directs the model to use a particular function.

For my scenario, `auto` is appropriate because some questions need a tool while other questions, such as asking for a motivational sentence, do not.

---

# 5. JSON Mode vs Schema Mode

JSON mode asks the model to return valid JSON, but it does not necessarily force the JSON to contain exactly the fields required by my application.

Schema mode is stricter because it defines the expected fields, types and constraints.

For example, for extracting a study request I can define:

- `subject`
- `priority`
- `needs_tool`

A tool is appropriate when the model needs my program to perform an action or calculation. A structured output is more appropriate when I only need information extracted into a predictable format.

Even perfectly shaped JSON does not guarantee a correct answer. The values can still be factually or logically wrong. Structure controls the shape of the data; it does not automatically verify the meaning.

---

# 6. Parallel Tool Calls

A model can return more than one tool call in a single response.

For example, a question can require both:

- information about Java, and
- a study-time calculation.

My loop therefore iterates through every item in `message.tool_calls`.

For each call, it appends exactly one tool message containing the matching `tool_call_id`.

Leaving one tool call unanswered can cause the conversation to become invalid because the assistant requested a tool result that was never supplied.

The question that combines subject information with a study-time calculation is the case designed to test multiple tool calls.

---

# 7. Failure Handling

Tool calls are generated text and can fail in several ways.

My implementation handles the following cases:

| Failure | Guard |
|---|---|
| Invalid JSON | JSON parsing error is returned as a message |
| Unknown tool | Available tool names are returned |
| Missing required argument | Validator reports the missing argument |
| Wrong type | Validator reports the expected type |
| Invalid enum value | Validator reports the allowed values |
| Invented argument | `additionalProperties: false` and validation reject it |
| Truncated response | `finish_reason = length` causes a retry with more tokens |
| Repeated identical calls | Repeat counter stops the loop |
| Tool execution error | Exception is converted into a tool error string |
| Wrong top-level argument shape | Validator requires a JSON object |

The important design decision is that these failures return strings rather than raising exceptions through the agent loop. The model can receive the error as a tool result and attempt a correction.

---

# 8. Repair Pattern

The repair pattern is:

**model request → parse → look up tool → validate → execute → return result/error → model retries if necessary**

Each stage returns a message instead of crashing the whole program.

A truncated response and a malformed tool call are handled differently.

A truncated response means the model did not have enough output space, so the appropriate repair is to increase `max_tokens` and retry.

A malformed tool call means the model generated invalid or unacceptable input. That information is useful to the model, so the error is returned as a message that explains what needs to be corrected.

---

# 9. Fault Injection

Fault injection means deliberately giving the tool handler broken inputs to verify that the guards work.

This can be done without a model and without internet because the test directly creates fake tool-call objects and passes them to the same handler used by the agent.

This is useful because waiting for a language model to make every possible mistake would be slow and unreliable. Fault injection makes the tests repeatable.

The main agent bugs are often around the boundary between the model-generated request and the application code: parsing, validation, tool lookup, execution and conversation state.

A stricter schema can prevent an invented argument or an invalid enum value.

A schema cannot prevent every problem. For example, it cannot guarantee that a semantically incorrect but correctly typed value is appropriate, and it cannot by itself prevent an unknown tool name from being generated.

---

# 10. Comparison: Tool Calling vs Structured Outputs

| Basis | Tool Calling | Structured Outputs |
|---|---|---|
| What the model is asked to do | Request an action from a defined function | Return data in a defined shape |
| Who performs the action | My Python code performs the function | The model produces the final structured data |
| How the shape is controlled | Tool argument schema | JSON/schema response format |
| What can still go wrong | Invalid calls, wrong values, repeated calls, execution errors | Correct JSON shape can still contain incorrect values |
| How my code guards against it | Parse, lookup, validation, execution checks, retry and repeat limits | Parse JSON and validate the resulting data where necessary |
| Support across servers/models | Depends on provider/model tool-calling support | JSON/schema support can vary between providers/models |
| Fetch or calculate something | **Tool calling** because my code must perform the action | Not the preferred choice |
| Extract fields from a sentence | Not necessary unless an action is also required | **Structured output** because I need predictable fields |

For my scenario, I would use tool calling when the system needs to calculate study time or retrieve subject information. I would use structured output when I only need to extract fields such as subject, priority and whether a tool is needed.

# 11. Fault Injection Observation

The fault-injection program tests the handler without requiring a model.

| Injected fault | Expected/observed handling | Run continued? |
|---|---|---|
| Valid call | Tool executes successfully | Y |
| Invalid JSON | Returns an invalid-JSON error message | Y |
| Unknown tool | Returns available tool names | Y |
| Missing argument | Returns the missing required argument | Y |
| Wrong type | Returns the expected type | Y |
| Invalid enum | Returns the allowed enum values | Y |
| Invented argument | Returns the allowed argument names | Y |
| JSON array instead of object | Returns that arguments must be a JSON object | Y |
| Wrong number type | Returns the expected numeric type | Y |
| Negative subject count | Reaches the tool's input handling rather than crashing | Y |

The important observation is that the handler returns a string for every tested case instead of allowing an exception to crash the program.

The deliberately injected faults therefore provide a repeatable test of the validation layer.

# 12. Agent Behaviour

The assessment requires four different types of questions.

| Question type | Purpose | Expected behaviour |
|---|---|---|
| Single-tool question | Test one tool | One tool call followed by a final answer |
| Multiple-tool question | Test parallel/multiple calls | More than one tool call can be processed |
| Invalid-value question | Test recovery/validation | Invalid arguments are rejected and returned to the model |
| No-tool question | Test direct response | Model answers without calling a tool |

### Single-tool example

**Question:** What is the recommended priority for Java?

The model should request `get_subject_info`.

### Multiple-tool example

**Question:** Tell me about Java and calculate the total study time for three subjects at two hours per subject.

This question can require both `get_subject_info` and `calculate_study_time`.

### Invalid-value example

**Question:** What is the priority for Java? Set the priority to urgent.

`urgent` is not one of the allowed enum values. The validator therefore rejects it instead of passing it directly to the function.

### No-tool example

**Question:** Write a one-line motivational message for a student.

No tool is necessary, so the model should answer directly.

---

# 13. Finish Reason and Retry

The agent checks `finish_reason` after every response.

If the reason is `length`, the agent doubles the token limit and retries, up to the configured maximum.

This is different from an invalid tool call. A malformed tool call is returned as a message so the model can correct it, while a truncated response is treated as insufficient output space and retried with a larger limit.

The repeat detector also prevents an agent from repeatedly making exactly the same unsuccessful call forever.

---

# 14. Before and After Guards

The main difference between an unguarded tool-calling loop and the guarded version is that the guarded version does not trust the model's arguments.

Without guards, malformed JSON, unknown tools, missing arguments or extra arguments can reach the execution stage and cause errors.

With the guards enabled:

1. JSON is parsed first.
2. The tool name is checked.
3. Arguments are checked against the schema.
4. Only validated arguments reach the function.
5. Errors are returned as messages.
6. Repeated calls and excessive steps are stopped.

Therefore, the guarded version is more reliable and easier to test.

---

# 15. Structured Output Observation

The structured-output demonstration compares three approaches.

| Case | Purpose | Result to record |
|---|---|---|
| No constraint | Shows normal free-form model output | Raw response and parsed result/error |
| JSON mode | Requires valid JSON but not necessarily the exact application schema | Raw JSON and parsed result/error |
| Schema mode | Requests the exact defined structure | Raw response and parsed result/error |

Provider support for strict schema mode can vary. If the provider reports that the response format is unsupported, that result is recorded as a provider limitation rather than treated as a programming failure.

---

# 16. Suitability of the Approach

The Student Study Planner is a suitable example for tool calling because the model needs to request real operations from application code. The calculation is not something that should depend only on generated prose; the Python function can perform the calculation deterministically.

Structured output is more suitable when the application only needs the model to extract information from natural language into predictable fields.

The most important guard is validation before execution. A model can generate syntactically valid JSON that still contains an invalid type, an unsupported enum value, a missing field or an invented field. Validation provides the boundary between generated text and executable application logic.

---

# 17. Conclusion

This assessment demonstrates that a model's tool call cannot be trusted simply because it comes from a tool-calling capable model. The call is still generated by the model and must be treated as untrusted input.

Every tool-calling loop should parse the generated arguments, verify the tool name, validate the arguments, execute only validated functions, return one result for every tool call, handle truncation, detect repeated calls and stop after a reasonable number of steps.

A JSON schema can prevent many structural mistakes such as missing required fields, invalid enum values and invented arguments. However, a schema cannot guarantee that the model's request is logically correct or that the resulting answer is factually correct.

Deliberate fault injection provides a repeatable way to test these protections without waiting for a model to fail naturally. This makes agent systems easier to debug and gives stronger evidence that the reliability guards actually work.

Overall, the assessment showed that reliable tool calling is not only about making a model call a function. The application must create a safe boundary around every model-generated call and recover from failures instead of allowing them to crash the agent.
